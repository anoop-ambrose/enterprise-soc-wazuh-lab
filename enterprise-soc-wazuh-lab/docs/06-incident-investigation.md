# 06 — Incident Investigation

# 1. Overview

This phase demonstrates the incident investigation process within the Wazuh-based SOC lab.

The investigation focuses on reviewing security events collected from the monitored CITADEL endpoint, identifying relevant activity, examining individual alerts, analyzing source and target information, and correlating the observed telemetry with the security activity generated during the previous lab phases.

The investigation is performed through the Wazuh Dashboard on SENTINEL.

---
# 2. Objective

The primary objectives of this phase were to:

- Review security events collected by Wazuh.
- Identify events requiring further investigation.
- Examine individual alert details.
- Analyze affected endpoints and source information.
- Review the original event logs.
- Correlate related security events.
- Identify relevant MITRE ATT&CK information where available.
- Document the investigation process from a SOC analyst perspective.

# 5. Alert Identification

Security events were reviewed to identify activity requiring investigation.

Examples of events observed within the lab include:

- SSH authentication failures

---
# 6. Alert Details

After identifying a relevant event, the individual Wazuh alert was opened to examine its complete event context.

The detailed event view provides additional information that is not immediately visible in the event table.

Relevant fields include:

| Field | Investigation Purpose |
|---|---|
| `@timestamp` | Establishes when the event occurred |
| `agent.name` | Identifies the monitored endpoint |
| `agent.ip` | Identifies the endpoint address |
| `data.srcip` | Identifies the event source when available |
| `data.url` | Identifies the requested web resource when applicable |
| `location` | Identifies the originating log source |
| `decoder.name` | Identifies how Wazuh parsed the event |
| `full_log` | Provides the original log information |
| `rule.description` | Describes the detected event |
| `rule.id` | Identifies the Wazuh detection rule |
| `rule.level` | Indicates the Wazuh rule severity level |

# 7. Source and Target Analysis

The next stage of the investigation is identifying the relationship between the source of an event and the affected endpoint.

For network or authentication-related events, relevant fields may include:

data.srcip
agent.name
agent.ip

For web-server activity, additional fields may include:

data.protocol
data.url

For example, an Apache event can provide the source address, requested resource, HTTP method, response code, and User-Agent.

This information can be correlated with activity generated from OCTOPUS during the controlled security-testing exercises.

# 8. Raw Log Analysis

The full_log field is particularly useful during incident investigation because it provides the original log information that was processed by Wazuh.

For web-server events, the raw log can provide information such as:

- Source IP
- Timestamp
- HTTP method
- Requested resource
- HTTP response code
- User-Agent

For example, during the directory-enumeration investigation, the raw Apache event contained a request generated by Gobuster:

### GET /externalization HTTP/1.1

with the User-Agent:

### gobuster/3.8.2

This type of raw-log evidence allows the analyst to correlate the SIEM event with the activity that generated it.

# 10. MITRE ATT&CK Context

Where Wazuh provides MITRE ATT&CK information for an alert, the analyst can use the associated technique and tactic to provide additional context.

For example, the SSH brute-force investigation in this lab produced a Wazuh alert associated with:

### MITRE ATT&CK ID: T1110
### Tactic: Credential Access
### Technique: Brute Force

The MITRE mapping provides standardized terminology for describing the behavior represented by the alert.

MITRE information should be treated as contextual enrichment rather than a replacement for analysis of the underlying event.

# 11. Investigation Process

The investigation workflow used in this lab can be summarized as follows:

## Step 1 — Review Security Events

Review the Wazuh event stream and identify unusual or security-relevant activity.

## Step 2 — Identify the Affected Endpoint

Determine which monitored agent generated the event.

Example:
### agent.name: CITADEL

## Step 3 — Examine the Event Source

Review source information such as:
## data.srcip
when available.

## Step 4 — Examine the Event Type

Review:
### rule.description
### rule.id
### rule.level
to understand why Wazuh generated the event.

# Step 5 — Examine the Raw Event

Review:
### full_log
to understand the original activity.

## Step 6 — Establish Timeline

Compare event timestamps with other events occurring around the same period.

## Step 7 — Correlate Related Events

Determine whether multiple events represent parts of the same activity.

## Step 8 — Apply Context

Use available MITRE ATT&CK mappings and other event metadata to provide additional context.

## Step 9 — Document Findings

Record the affected endpoint, source, activity, evidence, detection information, and investigation result.

# 14. SOC Analyst Investigation Perspective

From a SOC analyst perspective, an alert should not be treated as an isolated record.

The analyst should determine:

- What happened?
- When did it happen?
- Which endpoint was affected?
- Where did the activity originate?
- Which service or application was involved?
- What evidence supports the event?
- Are there related events?
- Does the activity correspond to known testing activity?
- Is there an applicable MITRE ATT&CK mapping?
- What additional investigation may be required?

The lab provides a controlled environment for practicing this investigation workflow.
